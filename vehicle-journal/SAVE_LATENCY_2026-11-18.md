# 상세기록 저장 지연 측정 — 2026-11-18

## 방법과 범위

운영 HA 서버의 SSH 앱 Python 3.14에서 측정했다. 운영 archive(약 404MiB)와
차계부를 SQLite read-only 연결의 backup API로 서버 임시 폴더에 복사했다.
생성자·초기 동기화·금액 수정·합계 계산·조회는 복사본에서만 실행했고, 종료 시
복사본은 제거했다. 운영 금액·사진·설정은 변경하지 않았다.

최신 main `004dfd7` 기반 실행 코드에서 기존 저장 경로와 개선 함수 `save_linked`를
각각 3회 실행했다. 동일한 복사본·기록을 사용하고 매번 금액을 다르게 수정했다.
실행 순서는 기존→개선, 개선→기존, 기존→개선으로 교대했다. 기존 경로는 저장 전후
`sync(force=True)`, 개선 경로는 기존 cursor/설정 검사를 사용하는 `sync()`다.
같은 스냅샷·투영·집계 함수에 계측 래퍼를 사용했다. 초기 준비 동기화는
16.50초였으며 아래 저장시간에서 제외했다.

이는 동일 서버의 복사본 비교다. 운영 HA 프로세스·브라우저 왕복·사진 업로드·
즐겨찾기 저장·UI 렌더링을 포함한 종단간 측정은 아니다. `/tmp`와 `/config`의
파일시스템 및 동시 부하 차이가 있을 수 있다. 운영에서 보고된 15~20초 요청을
직접 재현하지 않았고, 복사본 측정에는 실제 runtime/journal 잠금 경합이 없다.
소표본이므로 장기 분포나 p95를 주장하지 않는다.

## 최종 구현 함수 비교 결과

단위: 초. 각 열은 3회 중앙값이다.

| 금액 저장 | 0.0349 | 0.0330 |
| 저장 후 동기화 | 2.2740 | 2.4011 |

저장시간 중앙값은 **약 45% 감소**했다. 저장 전체 실측은 기존
`5.0609 / 4.5591 / 4.5496`, 개선 `2.4309 / 2.4982 / 2.7895`다.
하위 스냅샷 읽기 누적 중앙값은 기존 3.7294초, 개선 1.9159초였다.
스냅샷·투영·일별 집계는 상위 동기화 시간에 포함되므로 별도로 더하지 않는다.

앞선 경로 탐색 비교도 각각 3회에서 4.7773초→2.5219초(약 47% 감소)였다.
최종 표는 새 `save_linked` 함수를 직접 호출한 결과를 사용한다.

## 변경과 정합성

`api.py`는 새 `vehicle_journal/save.py`의 저장 함수를 executor에서 실행한다.
전체 동기화를 무조건 강제하는 대신 기존 동기화 함수의 generation·SOC 용량·
SOC 표시 버전·충전 편집 버전 검사를 사용한다.

- archive가 바뀌지 않았다면 저장 전 전체 주행·충전 스냅샷을 생략한다.
- 결제 수정은 기존 durable payment_outbox와 charge_payment 원본 쓰기를 유지한다.
  원본이 바뀌면 generation이 증가하므로 저장 후 전체 투영은 완료해야 성공한다.
- 새로운 원본 기록이 있거나 SOC 기준 등이 바뀌면 기존 전체 동기화로 돌아간다.
- 원본 결제 쓰기나 후속 투영 실패 시 기존 큐/미승인 cursor를 통해 복구한다.
- 기기 연결 차량의 수동 지출만 수정하고 원본이 그대로면 양쪽 전체 투영을 생략한다.

이번 변경은 대상 결제만 투영하는 새 체계를 만들지 않는다. 측정에서 확인된 중복
작업을 줄이며 기존 동기화·권한·버전 충돌·실패 복구 규칙을 유지한다.

## 실제 간헐 지연을 구분하는 로그

`Journal save timing` 로그에 전체시간과 `runtime_lock_wait`, `executor_wait`,
`journal_lock_wait`, `sync_before`, `save_manual`, `sync_after`, `read_version`,
`charge_totals` 시간을 밀리초로 남긴다. 2초 이상은 WARNING, 더 빠른 요청은 DEBUG다.
차량/기록/요청 식별자·금액·메모·위치·토큰·payload는 기록하지 않는다.

실제 느린 저장이 다시 발생하면 이 로그로 잠금/작업 큐 대기와 동기화 비용을 구분할
수 있다. 로그가 짧은데 화면만 느리면 브라우저 왕복·후속 즐겨찾기·조회 구간을
추가 조사해야 한다. 초기 준비 동기화 16.50초를 실제 사용자 지연의 원인으로 단정하지 않는다.

## 재현과 검증

`scripts/profile_journal_save.py --root <integration-root> --data <HA-carrot-data> --mode compare --runs 3`
명령을 서버에서 실행한다. 개선 비교에는 새 `vehicle_journal/save.py`가 포함된 소스를
사용한다. 이 도구는 임시 백업을 생성한 뒤에만 쓰기를 수행한다.

- Python 3.14 + 임시 폴더의 Pillow에서 차계부 전체 143건 통과. 이후 추가한 진단
  로그 검사까지 신규 저장 회귀 7건 통과(전체 검사와 6건 중복).
- 기존 충전 결제 14건, 스키마 9건 통과.
- 신규 회귀: 저장 후 금액·날짜 집계·버전 일치, 수동 지출의 불필요한 스냅샷 없음,
  새 원본 기록/용량 변경 시 투영, 오래된 편집 충돌, 결제 쓰기/투영 실패 후 복구,
  진단 로그 형식 확인.
- Mac 기본 Python 3.9의 전체 검사는 Pillow 미설치와 기존 tempfile 옵션 미지원으로
  14건 오류가 발생했다. 운영 서버의 격리된 Python 3.14 환경에서 전체를 다시 검증했다.
- 운영 파일 반영과 실행 중 적용은 별개다. Python 변경 적용을 위한 HA 재시작은 사용자가 수행한다.
