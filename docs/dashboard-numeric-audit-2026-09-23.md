# 대시보드 수치 표시 점검

- 기준: `1a9ee23`, 2026-09-23.
- 범위: 디버그 후보 1~5, 한국어/영어 메인 대시보드, Dashboard API의 `values()`, 충전시간 계산, 주행/충전 이력과 배터리 사용량의 데이터 계약.
- 제외: 이전 리뷰의 순간 전력에 따른 누적 요금 재계산 문제, 오프라인 잠금·주행가능거리 덮어쓰기 문제.
- 방법: 소스 대조, 실제 JS 렌더링 함수가 반환한 HTML 검증, Python 백엔드 함수 실행, 경계값·누락값 재현. 운영 Home Assistant 연결이나 실제 차량 계측값 검증은 수행하지 않았다. 디자인의 시각적 잘림 여부는 이번 수치 점검에 포함하지 않는다.
- 코드 수정/메인 반영 없음. 아래 결과는 현재 코드의 동작을 재현한 감사 기록이다.

## 결론

후보 화면의 계산/데이터 대체 로직을 그대로 메인에 옮기면 안 된다. 특히 주행가능거리, ETA, 세션 충전금액은 API 값을 표시하도록 연결해야 한다. 미리보기의 고정 데이터와 계산기는 운영 데이터의 검증 기준으로 사용할 수 없다.

## 1. 주행가능거리: API 필드 불일치와 임의 계산

위치: `frontend/carrot-dashboard-debug.js:563-564`, `2009-2011`; `vehicle.py:177-196`.

- API가 반환하는 값은 `range_km`이다. `estimated_range_km`는 API 필드가 아니다. 엔터티 ID에 붙는 `estimated_`와 API 키를 혼동하면 안 된다.
- 후보 화면은 `v.estimated_range_km`만 읽고, 없으면 `SOC × 4.6`으로 다시 계산한다. API의 전비 기반 `range_km`를 무시한다.
- 실제 백엔드 재현: 배터리 57,720Wh, 설정 용량 78kWh → SOC 74%, `battery_kwh=57.7`, 기본 전비 적용 `range_km=288`.
- 이 데이터를 후보 화면에 전달하면 340km가 표시된다. 후보 1~5 모두 같은 문제다. 동일 배터리에서 API 대비 52km 증가한다.
- SOC도 없으면 `—%`와 함께 **0km**가 표시된다. 실제로는 주행가능거리를 알 수 없는 상태다.
- 메인 차량 정보 탭은 `range_km`를 읽으므로 새 배터리 카드와 서로 다른 거리를 표시하게 된다.

반영 기준: `range_km`를 표시하고, 미수신 값은 `—`로 남긴다. 추정 근거는 백엔드의 `range_efficiency_basis`를 사용할 수 있다.

## 2. 충전시간: 운영과 다른 계산기로 경계값 오표시

위치: `frontend/carrot-dashboard-debug.js:30-215`, `568-577`; `battery.py:58` 이후.

- 디버그 계산기는 호출마다 EMA·180초 제한을 적용하는 구버전이다. 운영은 측정 시각, 에너지 증가량, 관측된 출력 감소를 사용하는 계산기다.
- 동일 조건 재현: SOC 99.9%, 78kWh, 11kW → 첫 계산 26초. 30초 뒤 SOC가 여전히 99.9%일 때 디버그는 **0초**, 운영 계산기는 **26초**를 반환한다. 디버그 카드에서는 0초를 ‘완료’로 표시한다.
- 실제 시뮬레이터에서 SOC 74%→100%로 변경하면 과거 ETA가 제한적으로만 보정되어 **100%인데 약 97분 남음**으로 표시된다(기본 용량 70.8kWh).
- 새로 초기화한 SOC 100%, 11kW, smooth 모드에서는 ETA가 0초이면서 충전 전력은 11kW로 남는다. curve 모드의 100% 출력 0kW 처리와도 다르다. 이 출력 자체는 실제 차량에서 불가능하다는 뜻이 아니라 시뮬레이터 모드 사이의 계산 일관성 문제다.

반영 기준: 메인은 `time_to_80_s`, `eta_80`, `time_to_100_s`, `eta_100`를 표시한다. JS 계산기를 운영에 복사하지 않는다. 시뮬레이터에서 SOC/시나리오를 바꿀 때는 계산 이력을 초기화하고 목표 도달 판정을 우선한다.

## 3. 현재 충전금액 누락 시 과거 충전량/상수로 대체

위치: `frontend/carrot-dashboard-debug.js:1981-1987`.

- `session_charge_kwh`가 없으면 `charge_energy_kwh`, 최근 완료된 충전 이력, 마지막으로 고정값 18.2kWh를 사용한다.
- 재현: 현재 세션 값이 전혀 없는 7kW 충전 화면에 **+18.2kWh, 5,096원**이 표시된다.
- 과거 완료 세션은 현재 진행 중인 세션의 충전량이 아니다. ‘추정’이라고 표시해도 이 대체는 성립하지 않는다.

반영 기준: 현재 세션의 API 값만 사용한다. 없으면 계산 중/정보 없음으로 표시한다. 이전 리뷰의 단가 변동 문제와 별개의 결함이다.

## 4. 11kW 경계와 비상충전 숫자/조건 불일치

위치: `frontend/carrot-dashboard-debug.js:590`, `1804-1805`; 한국어/영어 메인 `overview()`의 `isFast`, `chargeLabel`.

- 메인과 후보 모두 `>=11`을 급속으로 표시한다. 충전 이력·월간 집계·단가 기준은 **11kW 이하 완속, 초과 급속**이다.
- 재현: 정확히 11.0kW가 메인에서는 ‘고속충전중’/‘Fast Charging’으로 표시되지만 동일 전력의 분류 기준은 완속이다.
- 디버그는 1.4kW 첫 샘플만으로 비상충전 플래그를 켠다. 운영은 신선한 데이터에서 저출력 상태가 300초 이상 지속되어야 한다.
- 상태 문구의 `(1kW)`는 고정 문자열이다. 실제 1.4kW도 `(1kW)`로 표시되므로 측정값처럼 읽힐 수 있다.

반영 기준: 경계를 `>11`로 통일하고, 비상충전은 API 판정을 사용한다. 문구의 고정 숫자를 제거하거나 ‘약 1kW대’라는 유형 설명과 실제 출력값을 구분한다.

## 5. 미리보기 배터리 용량과 주행 이력 SOC의 기준 불일치

위치: `frontend/carrot-dashboard-debug.js:4`, `520-524`, `1508-1514`.

- 현재 배터리와 ETA는 70.8kWh 고정 용량을 사용한다. 운영 기본 설정은 78kWh이며 사용자 설정으로 변경할 수 있다.
- 미리보기 첫 주행은 출발 에너지 59,400Wh와 출발 SOC 76.2%를 동시에 넣는다. 76.2%는 78kWh 기준이다. 화면의 70.8kWh 기준으로는 **83.9%**가 되어야 한다.
- SOC 74%, 11kW의 단순 초기 조건에서 100%까지 시간은 70.8kWh 기준 **6,024초**, 78kWh 기준 **6,637초**로 약 10분 차이가 난다.
- 70.8kWh가 실제 차량에 틀린 물리량이라고 단정하는 문제가 아니다. 한 미리보기 안에서 서로 다른 용량 기준을 사용하는 것이 문제다.

반영 기준: 운영은 설정된 `soc_capacity_kwh`를 그대로 사용한다. 미리보기의 현재 에너지, 주행 출발·도착 SOC, ETA도 같은 용량 설정에서 생성한다.

## 6. 미리보기 월간 충전요금이 구성 충전량과 맞지 않음

위치: `frontend/carrot-dashboard-debug.js:531-534`.

- 완속 45.5kWh + 급속 110.4kWh = 전체 155.9kWh: 충전량 합계는 맞는다.
- 코드가 명시한 기본 단가 적용: 45.5×280 + 110.4×320 = **48,068원**.
- 미리보기 표시: **43,650원**, 차이 **4,418원**.
- 이는 미리보기의 고정 데이터 모순이다. 실제 백엔드 월간 원장의 금액이 동일하게 틀렸다는 증거는 아니다. 실제 원장의 구간별 반올림과도 구분해야 한다.

반영 기준: 미리보기 금액을 충전량·단가에서 생성하고, 운영에서는 `month_charge_cost`를 표시한다.

## 7. 기존 메인의 현재 속도 출처 설명이 부정확

위치: `frontend/carrot-dashboard-ko.js:525`; `vehicle.py:36-40`.

- ‘실시간 계기판 속도’로 설명하지만 표시 필드 `speed_kph`는 GPS의 `speedMps × 3.6`이다.
- 별도의 `wheel_speed_kph`가 존재한다. 재현 입력 GPS 10m/s, 휠 20m/s에서 API는 각각 36km/h, 72km/h를 반환하고 화면은 **36km/h를 계기판 속도라고 표시**한다.
- 극단적인 입력은 출처 차이를 확인하기 위한 재현이다. 실제 계기판 표시와 휠 속도도 항상 같다고 가정하면 안 된다.

반영 기준: GPS 값을 유지한다면 설명을 ‘GPS 속도’로 바꾼다. 휠 속도를 사용할 경우에도 ‘휠 속도’라고 출처를 표시한다.

## 8. 서버와 브라우저 시간대가 다르면 날짜/시간이 서로 어긋남

위치: 한국어/영어 메인 파일 상단의 `time`, `timeOnly`; `carrot-trip-days.js:1-25`; 디버그 `formatEtaCompletion`.

- 날짜 그룹은 HA `time_zone`으로 계산한다. 시각 문자열과 후보 ETA의 오늘/내일 판정은 브라우저 로컬 시간대를 사용한다.
- 재현: HA Asia/Seoul, 브라우저 UTC, `2026-09-22T15:30:00Z` → **9월 23일 그룹**에 속하지만 문자열은 **9월 22일 오후 3:30**이다. 서울 기준은 9월 23일 00:30이다.
- HA와 브라우저가 모두 한국 시간대이면 이 차이는 발생하지 않는다.

반영 기준: 날짜 그룹, 시각, ETA의 상대 날짜, 월간 fallback 집계가 같은 명시적 시간대를 사용하도록 한다.

## 기타 경계 표기

- `chargeDuration`은 분 단위 반올림을 사용하므로 1~29초가 **0분**으로 표시된다. `완료`와 구별되지만 ‘1분 미만’이 정확하다.
- 79.9%는 큰 SOC 숫자에서 80%로 반올림되지만 ETA 목표 선택은 원래 79.9%를 사용하므로 ‘80%까지 남음’과 같이 표시될 수 있다. 99.9%/100%도 같은 종류의 표현 문제다. 목표 판정을 표시 반올림값에 맞추기보다는 소수점 또는 미만 표기를 사용하는 편이 안전하다.
- 기존 충전 탭은 누락된 월간 요금을 `0`, 이력이 없는 완속/급속량을 `0`으로 대체한다. API 정상값과 미수신 상태를 구별하려면 `—`가 필요하다. 현재 정상 API는 대부분 이 필드를 채우므로 주로 빈 화면/부분 데이터에서 드러난다.

## 검증 기록 및 반영 조건

- 기존 JS 6개 파일 통과: `charging-curve`, `charging-layout-metrics`, `debug-freshness`, `motion-status`, `trip-days`, `trip-ui`.
- 별도 재현으로 후보 1~5의 거리 표시, 누락 세션 금액, ETA 99.9%/100% 경계, 11kW 분류, 미리보기 월간 수치/용량 불일치를 확인했다.
- 기존 테스트가 통과해도 운영 API와 미리보기의 숫자 일치를 보증하지 않는다. 일부 테스트는 구버전 미리보기 계산기의 현재 동작을 기대한다.
- 반영 전 필수: API 필드로 연결한 동일 입력에 대해 메인·후보 1~5의 값 일치, null→정보 없음, 충전 목표 도달, 11kW 경계, 시간대 차이 회귀검증.
- 현재 결과는 ‘수치 표시 점검 완료, 발견 사항 미수정’이다. 메인 반영 가능 판정은 수정 후 위 조건을 확인해야 한다.
