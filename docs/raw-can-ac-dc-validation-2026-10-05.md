# 2026-10-05 AC/DC 실차 CAN 대조 분석

사용자가 기록한 AC/DC 세션을 HA 원시 CAN 및 HA archive의 제한된 차량 필드와 대조했다.
시각은 한국 시간이다. 개인 메모 원문, 위치, 인증 정보, 원시 파일은 이 보고서에 포함하지 않는다.
실행 코드 변경 없이 분석 기록만 추가한다.

## 자료와 방법

- 새 세션 gzip 1,924개, 압축 데이터 258,524,170바이트, 전체 26,156,882프레임.
- 수신 범위 13:08:09.855993~14:45:44.572430. gzip 해독 오류 0, reported dropped_frames 최대 0.
- 13:11:11~13:12:05에 53.8초 공백이 있으나 AC/DC 실험 구간에는 해당 공백이 없다.
  보고된 드롭 0이 차량의 모든 버스/메시지 수신을 보장하지는 않는다.
- 각 파일의 unix_ns/boot_ns anchor로 프레임 수신 시각을 복원하고 시간 정렬했다.
  물리 source bus 0/1/2와 송신·거절 플래그 source를 구분했다. 아래 주요 신호는 bus 1이다.
- 후보 선별은 배치 첫 프레임, 모드 전이·전력·범위 검증은 해당 ID 전체 프레임을 사용했다.
- 사용자 시계, 차량 표시, 충전기 표시는 독립적인 기록이다. 수 초 차이를 기기의 응답 지연으로 단정하지 않는다.
- 전력 적분은 0xCF의 유효 전류×전압을 시간 정렬한 뒤 사다리꼴 방식으로 수행했다.
  0<간격≤0.1초 구간만 포함했고, 해당 충전 구간에서 제외된 양의 공백은 0초였다.

## 충전 여부: AC와 DC 모두 독립 대조에 성공

| 구분 | 사용자 기록 시작/종료 | BMS 실제 모드 0xCF 전이 | HA 기록 전이 |
| --- | --- | --- | --- |
| AC | 13:31:30 / 13:55:38 | 13:31:27.164 코드4 / 13:55:36.415 코드1 | 13:31:39 ac_charging / 13:55:39 hv_on |
| DC | 14:12:00 / 14:26:40 | 14:11:52.723 코드6 / 14:26:38.138 코드1 | 14:12:10 dc_charging / 14:26:41 hv_on |

현재 beta.8의 충전 여부는 **HVK 요청 모드 0x503**, source `can_request`로 결정된다.
이번 분석에서 **BMS 실제 모드 0xCF**도 AC=4, DC=6으로 일치해 요청 신호를 독립적으로 뒷받침했다.
두 충전 종료 뒤 사용자가 플러그를 유지한 구간에서도 실제 모드는 코드1로 돌아갔고 전력은 소량 소비 방향이었다.
따라서 연결된 채 충전하지 않는 상황을 충전 중과 구별할 근거가 있다. 실제 모드만으로 플러그 연결 여부를 확정할 수는 없다.

DC 14:13:47에 요청 모드가 약 9.8ms 코드7로 흔들렸지만 실제 모드는 코드6을 유지했다.
후속 개선은 실제 모드를 우선하고 요청 모드를 보조 근거로 사용하는 방향이 타당하다.
이번 분석만으로 실행 코드를 바꾸지는 않았다. CRC/카운터의 전체 검증이나 제조사 인증을 의미하지 않는다.

## 실제 충전 속도: 수동 전류 변경까지 포착

0xCF: mode=byte2&7, current=(((byte4&127)<<8|byte3)-16300)×0.1A,
voltage=(byte7<<4|byte6>>4)×0.25V. 이 차량에서는 양의 전류가 충전 방향이다. 초기화 mode7은 제외한다.

- 일반 AC 구간 전력은 대체로 6kW대였으며 최대 6.50kW였다. 차량 화면 6.5kW와 방향·규모가 맞는다.
- AC 전류 낮추기를 켠 뒤 안정 구간 13:51:40~13:53:15의 시간 평균은 **1.447kW**였다.
  사용자가 13:53:20 차량 화면에서 기록한 1.5kW와 가깝다. 해제 후 6kW대로 복원됐다.
- DC 실제 충전 구간 시간 평균은 **71.089kW**, 최대 **74.177kW**였다. 충전기 화면 약72kW와 규모가 맞는다.
  표시 시각별 값은 완전히 같지 않으므로 충전기 표시와 배터리 측 측정값을 동일시하지 않는다.

**현재 HA의 charge_power_w는 실제 전류×전압이 아니다.** engine.py는 battery_wh의 시간 차분으로 계산한다.
13:52:45 HA는 0W, battery_wh=13,650Wh를 기록했지만 안정 구간 CAN 전력은 약1.45kW였다.
13:53:45에는 HA 5,899W가 기록돼 변화 시점이 지연·양자화될 수 있음도 확인했다.
충전 상태 판단과 충전 속도 계산은 서로 다른 경로다. 후속 릴리즈에서 실제 전력 필드를 사용하는 개선 근거다.

| 총량 비교 | AC | DC |
| --- | --- | --- |
| 충전기 종료 총량(사용자 기록) | 2.610kWh | 17.826kWh |
| CAN 전력 적분(실제 모드 구간) | 2.349kWh | 17.484kWh |
| Motor_16 잔여 에너지 증가량 | 2.375kWh | 16.900kWh |

측정 위치, 보조 소비, 표시 시점, 에너지 추정·양자화가 다르므로 차이를 모두 충전 손실이나 센서 오차로 해석하면 안 된다.
특히 낮은 AC 전력 구간에서 잔여량이 일정하게 보고되더라도 실제 충전이 계속 진행될 수 있다.

## 목표 SOC: 이번 변경 실험에서도 필드를 찾지 못함

50→60→70→80→90→100→60% 설정 변경을 대조했다.
기존 0x5A2 bit53|11×0.05 필드는 전체 11,607프레임에서 계속0으로, 사용자 목표 SOC를 나타내지 않았다.

추가 탐색은 모든 수신 물리 버스의 메시지에 대해 각 변경 후20초~다음 변경 전10초 구간을 비교했다.
최소5표본/단계, 단계별95% 이상 안정, little/big endian의 3~16bit 필드, 7단계와 선형 대응하는 패턴을 검색했다.
일치 후보는 0개였다. 이는 **이 탐색 조건에서 못 찾았다는 뜻**이다.
이벤트성 전송, 다른 인코딩, 미수신 버스, 변동 필드는 놓칠 수 있어 “CAN에 목표 SOC가 없다”고 단정할 수 없다.
0을 실제 목표로 노출하는 것은 적절하지 않다. 목표 SOC 엔터티 추가 근거는 아직 부족하다.

AC 전류 낮추기와 함께 변한 비트 중 0xCF bit31~38은 실제 전류 숫자 내부이고,
0x16A954A6 bit44는 셀 전압 숫자 내부다. 이들을 설정 스위치 신호로 오인하면 안 된다.
0xC0 bit58도 변했으나 의미가 확인되지 않았고 반복 실험이 없어 직접 설정 신호로 채택하지 않는다.

## 신규 배터리 엔터티와 SOC 후보

- 팩 최저/최고 온도: AC 약18.5~19 / 19~19.5°C, DC 약19→30 / 19.5→31.5°C.
  HA 종료 기록에서도 30/31.5°C로 확인됐다. 종료 뒤 최고32°C까지 관찰됐다.
- 충전 적정 온도: AC는 below_optimal, DC 중 below_optimal→optimal로 전환.
  HA도 종료 시 optimal이었다. 관찰된 전환만으로 모든 상황의 고정 온도 임계값을 추정하지 않는다.
- 셀 최대−최소 전압: AC5~10mV, DC5~12mV. 사용자 관찰8mV와 같은 범위이며
  HA 종료 표본7mV였다. 서로 다른 시각의 7/8mV 차이는 불일치 증거가 아니다.
- 0x14A 32byte의 byte19×0.5%는 계기판 SOC 후보:
  14:14:40 CAN26%, 메모26%; 14:17:00 CAN30%, 메모30%로 독립 대조가 강화됐다.
  그러나 13:43:35 CAN20%/메모19%, 14:26:00 CAN46.5%/메모47% 등 차이가 있다.
  표시 반올림/갱신/시계 차이를 추가 확인해야 하므로 모든 순간에 정확히 같다고 단정하지 않는다.
- BMS 자체 SOC와 계기판 SOC는 다르다. 구분 없이 기존 SOC를 대체하지 않는다.

## 쓰면 안 되는 단독 충전 근거

0x1A555550 bit16의 후보 charging_active는 AC 시작 뒤 약8분30초 후에1이 됐고,
AC 종료 뒤에도 약4분30초간1을 유지했다. DC도 시작 약45초 후1, 종료 약3분30초 후0이었다.
따라서 실제 충전 시작/종료의 단독 판정 신호로 부적합하다.
0x12DD54D0의 최대 충전 허용 전력은 AC에서도 약101kW로, 실제1.5/6.5kW를 따라가지 않았다.
허용 한도와 실제 충전 속도를 구분해야 한다.

## 후속 적용 우선순위

1. BMS 실제 모드 0xCF를 충전 판정 우선 근거로 사용하고 HVK 요청 모드와 불일치를 기록.
2. 실제 전류·전압과 배터리 측 전력을 수집해 충전 속도의 잔여량 차분 계산을 개선.
3. 목표 SOC는 미확인 상태 유지, 계기판 SOC 후보는 추가 표시 대조 후 적용 판단.

분석 보고서·색인만 갱신한다. HA/Comma 실행 코드, GitHub Release, Worker/D1 변경은 없다.
원시 CAN과 사용자 입력 원본은 보존했다.
