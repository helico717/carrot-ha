# ID.4 센서 분석 및 HA 변경 (2026-09-23)

## 분석 범위

첨부 SQLite는 읽기 전용으로 열었다. 01M20PX3RFCPQMVYWXQ6GCKZKX는 9월 8일 테스트 이벤트 6건뿐이다. 실제 분석은 01M23RJD5A9H29TRSYCXV4HJ80의 state 17,510건, charge 27건, trip 89건을 사용했다. 원시 CAN 프레임이나 현재 실행 중인 HA의 엔터티 레지스트리는 포함되어 있지 않다.

## 1. 극저속 충전 전력 0 kW

HA는 수신 W를 1,000으로 나눠 소수 한 자리로 표시한다. 1,500 W를 0으로 만드는 변환은 없다. 실제 DB에는 charging=true이면서 charge_power_w=0인 state가 19건 있다.

collector/engine.py의 _sample_energy는 약 90초 이상인 비중첩 구간에서 배터리 저장 에너지 증가량 × 3,600 / 경과초로 전력을 계산한다. 300 W 미만이면 0을 저장한다. 저속 충전에서 에너지가 계단식으로 갱신되거나 잠시 증가하지 않으면 0이 생기고, 다음 구간에서는 다시 약 1.5~2 kW가 나온다. 이것은 충전기 입력 전력의 직접 측정이 아니다.

예: 9월 23일 10:00:27~10:10:28 KST, 43,050→43,250 Wh. 601초 평균은 약 1.20 kW지만 중간에 원본 전력 0이 있다. 충전기에서 표시한 1.5 kW와 배터리에 저장되는 순전력은 보조 소비·손실 및 측정 갱신 때문에 다를 수 있다. 해당 DB만으로 충전기 입력 전력은 검증할 수 없다.

권장 HA 개선 설계:

- 수신 시점이 아닌 field_measured_at.battery_wh 기준으로 중복을 제거하고, 5~10분 에너지 변화로 저속 구간 순충전 전력을 추정한다.
- 5분 미만 또는 측정 단절·역순·주행 전환·에너지 감소 시에는 보완 추정치를 사용하지 않는다. 시작 시에는 아직 계산 불가로 표시한다.
- 최근 증가가 멈췄을 때 과거 전력을 무기한 유지하지 않는다. 전력에 사용한 구간과 계산 출처를 속성으로 표시한다.
- 전력 표시 보완과 충전 세션/충전량 장부 변경은 분리한다. 배터리 순증가만으로 플러그 연결이나 실제 비상 충전을 확정하지 않는다.
- DB 재생으로 저속뿐 아니라 정상 완속, 급속, 충전 종료, 재시작, 통신 단절을 함께 검증해야 한다.

이번 요청의 ‘방안 고민’에 맞춰 원인과 설계를 제공하며 전력 계산 알고리즘은 변경하지 않았다. collector 파일도 변경하지 않았다.

## 2. BMS 모드

값이 존재하는 1,565건 전부 hv_inactive다. 이 중 driving=true 547건, charging=true 81건도 같은 값이다. 현재 collector는 BMS_04.BMS_IstModus의 0을 hv_inactive로 매핑한다. 로컬 vw_meb DBC의 0=HV_inaktiv 정의와 일치하므로 HA의 번역 문제는 아니다.

CAN 통신이 살아 있다는 사실은 해당 비트가 유효한 운행 상태를 제공한다는 뜻이 아니다. 해당 차량/버스에서 미사용·고정된 신호이거나 차량과 DBC가 맞지 않을 가능성이 있으나, 원시 프레임 없이 어느 쪽인지 확정할 수 없다. 기어/충전 추정을 BMS 하드웨어 모드로 대신 표시하지 않는다. 사용자용 bms_mode 센서를 생성하지 않고 기존 레지스트리 항목도 다음 통합 로딩 때 제거한다. 원본 데이터는 보존한다.

## 3. BMS 목표 SOC

1,565건 전부 0이며 충전 중에도 동일하다. BMS_04.BMS_Soll_SOC_HiRes는 collector에서 0~100을 허용하므로 0이 그대로 HA에 전달된다. DBC 배율은 0.05이며 Init/Error 원시값은 2046/2047이다. 따라서 0을 DBC가 정의한 오류값이라고 단정할 수도 없다.

이 신호가 차량 화면의 충전 상한 SOC를 나타낸다는 증거가 없다. HA에서 실제 80%/100% 설정을 복원할 방법도 없다. 임의의 목표값으로 바꾸지 않고 원본 신호 센서를 진단 항목으로 분류했다. 기존 source 및 vehicle_charge_limit_verified=false 속성을 유지한다.

## 4. 월 전비 보조 센서

- month_energy_coverage_percent: 이번 달 기록된 주행거리 중, 전비 계산에 사용할 배터리 에너지 자료가 확보된 주행거리의 비율. 배터리 충전율이나 차량 전체 운행의 수집률이 아니다.
- month_drive_energy_kwh: 위 유효 주행들의 출발/도착 배터리 저장 에너지 차이의 합. 회생 증가도 부호를 유지하며, 누락/부분 주행은 제외한다. 월 전체 소비전력이나 충전기 전력량이 아니다.

전비 계산은 유효 주행거리 / 해당 순소모 에너지다. 두 값은 사용자용 독립 센서보다 계산 품질 진단에 적합하므로 엔터티를 제거한다. 월 전비 센서의 coverage_percent, distance_km, energy_kwh 속성과 내부 집계는 유지한다.

## 5. 추정 이름

실제 state 17,510건 모두 range_km이 없다. HA는 저장 에너지 × 전비로 계산하며, 월 유효 전비 → 최근 주행 전비 → 자료가 적은 월 전비 → 기본 5 km/kWh 순으로 선택한다.

주행가능거리 (추정), 충전 전력 (추정), BMS 용량 (추정), 월 전비/충전량/충전요금, 충전 예상 시간, 충전 추정 상태에 괄호 표기를 적용했다. 해당 추정 엔터티의 기본 ID에는 estimated를 넣는다. 기존 기본 ID도 이전한다. 예: sensor.id_4_range_km → sensor.id_4_estimated_range_km. 충전 전력은 이미 estimated_charging_power다.

unique_id는 유지한다. 사용자 지정 ID와 목적 ID 충돌은 보존한다. 사용자 지정 표시 이름은 덮어쓰지 않는다. 문자열로 이전 ID를 참조하는 사용자 자동화/대시보드는 업데이트가 필요할 수 있다. 내부 대시보드는 원래 데이터 키를 그대로 사용하며, 충전 상태 ID 조회도 unique_id를 사용한다.

## 6. Comma 헬스

CPU/GPU 온도, CPU/메모리 사용률, 여유 저장공간, 팬 목표 출력, 발열 상태, 네트워크 종류/세기 9개 필드가 각각 1,565건 저장되어 있다. 마지막 기록에는 CPU 48.1°C, GPU 46.1°C, CPU 9.5%, 메모리 43%, 저장공간 잔여 30%가 존재한다. 따라서 이 기록 기준으로 collector → 클라우드 → HA 저장 경로는 동작한다.

기존 코드는 모든 엔터티를 Volkswagen ID.4 기기에 넣고, 헬스를 diagnostic으로 분류한다. 별도 Comma 기기가 없었던 것은 기기 소속 정의 때문이다. 실제 UI에서 전혀 보이지 않았던 원인이 비활성화/숨김/설치 버전 중 무엇인지는 첨부 DB로 알 수 없다. 필드 타임스탬프가 없거나 180초가 지나면 값이 unknown으로 바뀌는 정책도 있다.

차량별로 독립된 식별자의 Comma 기기를 만들고 헬스 9개와 comma_online 연결 상태를 이동한다. 기존 unique_id와 entity_id는 유지한다. 헬스의 180초 신선도 정책을 유지하며 차량 CAN이 잠들어도 신선한 deviceState가 오면 헬스 값은 표시된다. 사용자가 비활성화한 항목을 강제로 활성화하지 않는다.

## 적용 및 검증

저장소의 HA 통합 소스만 수정했다. 실제 HA 서버에 배포하거나 재시작하지 않았다. 업데이트 설치 후 HA 재시작 또는 통합 재로딩 때 엔터티 제거/이름 이전/Comma 이동이 실행된다. collector와 첨부 DB는 수정하지 않았다.

Python 테스트 67개 통과. 엔터티 이전 재실행, ID 충돌/사용자 ID 보호, Comma 소속 이전을 검증했다. 충전 레이아웃·주행 상태·데이터 신선도 JavaScript 테스트 3개 통과. 실제 HA 환경에서의 레지스트리/UI 확인은 배포 후 필요하다.

레지스트리 API 확인: https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/helpers/entity_registry.py


## 후속 반영: 급속 응답 유지와 잠금 통합

이 절은 앞의 ‘전력 계산 알고리즘 미변경’ 및 5~10분 보완 제안에 대한 후속 변경이다. 장시간 초기 대기 대신 HA 표시 단계에서 제한적으로 직전 전력을 유지한다.

- 양수 원본 전력은 급속/완속 구분 없이 즉시 반영한다. 급속 시작, 출력 상승, 테이퍼링에 추가 평균 대기가 없다. collector 자체의 측정 구간 지연은 그대로다.
- 충전 중이고 주행 중이 아니며 배터리 측정이 신선할 때, 0 W가 들어오면 직전 양수 전력을 유지한다. 이전 전력이 11 kW 이하이면 첫 0 측정부터 최대 180초, 초과이면 최대 60초다. 이는 충전기 종류 판정이 아닌 표시 유지 시간 구분이다.
- 반복 읽기/연속 0은 유지 시간을 연장하지 않는다. 종료, 주행, 데이터 만료/누락, 180초 초과 측정 공백, 역순 측정 시 유지 상태를 해제한다. 새 양수는 바로 반영한다. HA 재시작 후 이전 양수가 없으면 임의로 복원하지 않는다.
- 유지 중에는 raw_power_w, source=held_last_positive, hold_age_s, hold_limit_s 속성을 제공한다. 배터리 측정 만료 시 전력은 unknown이다. 충전량 장부는 바꾸지 않는다. 비상충전 판정은 보완 표시값 대신 원본 전력을 계속 사용한다.
- 실제 종료 후 charging 추정이 잠시 켜져 있으면 종료 표시도 유지 시간만큼 늦어질 수 있다. 플러그/실전력 신호가 없는 상태에서 0 튐과 즉각적인 종료 감지를 동시에 완벽하게 구별할 수는 없다.

첨부 실제 DB를 관측 시각 순서로 재생한 결과 충전 중 0인 19건 중 18건에 유지 보완이 적용됐다. 신선한 양수 원본 1,695건의 값을 다른 전력으로 대체한 경우는 없었다. 이는 기록 재생 결과이며 차량 실시간 검증은 아니다.

잠금 엔터티는 binary_sensor의 doors_locked(차량 잠김 상태) 하나로 통합했다. 동일 시점 내부/외부 신호 중 하나라도 true이면 켜짐, 둘 다 false이면 꺼짐, 자료 부족 또는 측정 시점 불일치이면 unknown이다. 이는 중앙 잠금 신호이며 모든 문이 물리적으로 닫혔음을 의미하지 않는다. 차량 수면 중에는 기존처럼 마지막 확인값을 유지하며 stale 및 원본별 측정 시각을 속성으로 제공한다. 내부/외부 값은 속성에 남기고 두 기존 엔터티는 통합 로딩 시 제거한다. ON=잠김 의미를 유지하기 위해 ON=해제인 HA lock binary device class는 사용하지 않는다.

후속 검증: Python 75개 통과(급속 초기/테이퍼링, 저전력 0 유지/만료, 신선도/공백/재시작/역순, 잠금 논리 및 기존 엔터티 제거 포함). collector 변경 및 실제 HA 배포는 하지 않았다.


## 추가 검토: 주차 중 잠금 유지 및 ETA 입력 분리

사용자 확인에 따라 잠금 통합에서 측정 시점 일치 조건을 제거했다. 내부/외부 각각 마지막 보고값을 OR로 결합하며, 180초 경과·stale·측정 시점 불일치로 값을 지우지 않는다. 하나라도 true이면 잠김, 둘 다 false이면 해제, 그 외 자료 부족이면 unknown이다. 신호가 갱신되지 않는 주차 중에는 마지막 상태를 유지한다. 오래된 내부 잠금 true가 더 최신 외부 해제 false와 결합되어 잠김으로 남을 수 있다는 한계는 사용자가 인지하고 수용했다. 이 정책은 차량 잠금에만 적용하며 Comma 헬스 및 충전 데이터의 신선도 검증은 유지한다.

전력 표시 보완 후 vehicle.values가 반환받은 held 전력을 estimate_charging_times에 그대로 전달하는 경로를 확인했다. 에너지 증가가 없거나 짧은 이력만 있을 때 이전 전력으로 학습하거나 ETA를 유지할 수 있어, 실제 저속화/정지 시 낙관적인 완료시각을 만들 위험이 있었다. 기존 ETA 알고리즘은 180초 이상 양의 에너지 증가 이력이 있으면 에너지 기울기를 우선하지만, 그 조건이 언제나 성립하는 것은 아니므로 이를 안전장치로 간주하지 않았다.

ETA 입력을 charge_power_raw_w로 분리했다. 직전 전력 유지값과 유지 한도(180/60초)는 완료시간 계산에 영향을 주지 않는다. 원본 0/누락이면 기존 ETA 계산 정책대로 80/100 예상시각과 남은시간은 unknown, 학습 상태는 초기화된다. 양수 원본 회복 시 현재 에너지와 새 전력으로 다시 시작한다. 따라서 전력 표시는 유지 중이지만 ETA는 unknown인 구간이 생길 수 있다. 이것은 직전 전력을 새 측정으로 간주하여 장시간 외삽하는 것을 방지하기 위한 명시적인 동작이다.

양수 측정 시 기존 알고리즘의 120초 전력 평활, 300초 에너지 이력, ETA 변화 제한은 유지했다. 완속 전력이 실제로 낮아질 때 기존 평활 때문에 반응 지연이 남을 수 있고, 100% 부근 감속·보조소비 변화·차량 충전 상한은 완전히 예측하지 못한다. 정확한 완료시간을 보장하는 변경은 아니며, 이번 전력 표시 유지가 추가로 ETA를 왜곡하는 경로를 제거한 것이다.

검증: Python 76개 통과. 1.5 kW 이후 원본 0이 반복되어도 표시만 유지하고 두 ETA 및 학습 상태는 비우는지, 이후 0.75 kW 회복 시 새 전력으로 재계산하는지 검증했다. 주차 중 stale 및 서로 다른 시각의 잠금/해제 값 유지도 검증했다. collector와 실제 HA 서버에는 변경하지 않았다.
