현재 적용 방식: 실시간 SOC는 `0x14A` byte19×0.5% 원본을 사용하고 정수 표시만
반올림한다. 원본/Recorder에는 0.5%를 보존한다. 주차 중에는 마지막 측정값과 측정시각·
stale 속성을 보존하고, 미수신/무효 신호를 Wh 계산 SOC로 조용히 대체하지 않는다.
주행·충전 경계는 양쪽 CAN SOC가 있을 때 함께 전환한다. 후보가 없는 과거 기록은
기존 환산 출처로 보존하고 에너지와 과거 기록 원본을 덮어쓰지 않는다. 서로 다른 출처의
기록은 SOC 차분/사용량 및 주행 병합에서 섞지 않는다. 별도 후보 엔터티는 제거 대상이며
기존 배터리 엔터티의 unique_id와 entity_id를 유지한다.

충전 80%/100% ETA의 에너지 모델은 이번에 변경하지 않아 표시 SOC가 목표를 지나는
시점과 ETA가 0이 되는 시점이 다를 수 있다. 실제 사용 중 별도로 확인할 항목이다.

## 64kWh 기준과 각 계산의 관계

64kWh는 현재 잔량 Wh를 표시 SOC로 환산하는 설정값이다. 이 값만으로 실제 사용 가능
용량, SOH, 숨은 버퍼를 확정할 수 없다. 계기판 후보를 채택해도 SOC%에서 역산해
원래 Wh를 덮어쓰거나 1%p를 항상 0.64kWh로 간주하면 안 된다.

| 항목 | 현재 근거 | 후보 채택 시 검토 |
| --- | --- | --- |
| 실시간 배터리 % | `vehicle.py` → `battery.calibrated_soc`: Wh/설정용량, 100% 상한 | 검증된 후보를 표시 출처로 쓸 수 있음. freshness·미수신 fallback·출처 표기 필요 |
| 저장 에너지 kWh | `battery_wh / 1000` | 유지. 후보% × 64로 대체하지 않음 |
| 주행 에너지·전비 | `trip_repair.py`, `storage.py`: Wh 차이와 실제 거리 | 유지. 0.5%p 단계의 후보로 kWh를 역산하지 않음 |
| 최근 50km 전비·예상 주행거리 | `_window_efficiency`, `vehicle.py`: Wh 차이 전비 × 현재 잔량 kWh | SOC 표시 변경만으로 바뀔 이유 없음. 잔량 에너지 자체 검증은 별도 |
| 차계부 주행 시작/종료 SOC, %p/100km | `_format_trip_energy`, `vehicle_journal/source.py` | 후보의 경계값·측정시각이 있어야 전환 가능. 거리·에너지 집계와 분리 |
| 충전 시작/종료 SOC·충전 %p | `enrich_charges_soc`: 경계 근처 Wh/설정용량 | 검증 후 후보 경계 우선순위 검토. 충전량 kWh와 별개 |
| 충전 kWh·단가·비용 | 충전 요약의 kWh 및 실제 청구/결제 | SOC 표시 출처 교체만으로 금액·kWh를 재작성하지 않음 |
| 80%/100% 도달시간 | `estimate_charging_times`: 설정용량·잔량 에너지·전력 | 표시 후보 목표와 Wh 목표가 어긋날 수 있어 별도 모델 검증 필요 |
| 배터리 사용 이력의 % 소모 | `battery_history.py`: Wh/설정용량의 감소분 | 표시 SOC 감소와 에너지 환산 소모를 구분. 그대로 후보 차분으로 바꾸면 계단/보정 영향 발생 |

후보의 0.5%p 한 단계는 64kWh 비례식으로 환산하면 0.32kWh다. 이는 신호의
표시 해상도를 설명하는 예이며 실제 단계당 소비 에너지가 0.32kWh라는 뜻이 아니다.
짧은 주행 전비·주차 소모량을 후보 차분으로 계산하면 해상도와 표시 보정의 영향을 받는다.

추가 발견: `_format_trip_energy`는 Wh가 설정용량(64,000Wh)을 넘으면 해당 경계 SOC와
Wh를 출력에서 비운다. 실시간 표시는 100%로 제한한다. 64,200Wh 같은 완충 부근에서
두 경로의 표시가 달라질 수 있으므로 후보 도입 검토에 포함해야 한다. 원본 DB와 검증된
Wh 기반 주행 에너지를 임의로 지우거나 재작성하지 않는다.

  출처 변경을 실제 배터리 변화로 오인하지 않도록 한다.
- 임시 센서는 기존 main `telemetry.py`를 HA에 백업 후 반영했다. 진단 분류, `%`,
  `measurement`, 180초 freshness를 사용한다. 기존 배터리 엔터티·계산은 유지한다.
- 사용자 HA 재시작 후 등록 ID·숫자 수신·Recorder/장기 통계 생성 확인이 필요하다.
  Recorder 원시 보관 설정은 7일이며 후보는 제외 대상이 아니다. 장기 통계는 집계값이고
  원시 이력/초 단위 CAN·실제 계기판 사진 대조를 대신하지 않는다.

## 정수 표시 정책 검토 — 사용자 추가 요청

표시는 정수로 하되 수신 원본·Recorder·주행 경계·비교 통계는 0.5% 정밀도로 보존한다.
표시 정수를 다시 에너지·SOC 소모량·충전 목표 도달 판정의 입력으로 쓰지 않는다.

| 원본 | 0.5 올림 반올림 | 버림(floor) | 올림(ceil) |
| --- | --- | --- | --- |
| 58.0% | 58% | 58% | 58% |
| 58.5% | 59% | 58% | 59% |
| 59.5% | 60% | 59% | 60% |
| 99.5% | 100% | 99% | 100% |
| 100.0% | 100% | 100% | 100% |

수집 신호가 0.5% 단위이므로 올림과 0.5 올림 반올림은 정상 후보 값에서 같은 결과가
나온다. 이를 모두 일반 실수 값에도 동일하다고 확장하지 않는다. 버림은 후보값이 100%에
도달하기 전에는 100%라고 표시하지 않는 장점이 있지만 계기판 방식이라는 증거는 없다.
반올림은 최댓값에서 99.5%를 100%로 표시하므로 표시 100%를 충전 완료로 해석하면 안 된다.
최종 선택은 실제 계기판에서 .5% 지점, 특히 99.5%를 동시에 대조한 뒤 확정한다.

구현 시 Python 기본 round()의 ties-to-even과 JS Math.round()/Intl 숫자 표시 정책을
혼용하지 않는다. 예를 들어 Python round(58.5)는 58, Math.round(58.5)는 59다.
모든 표시 경로에 명시적인 같은 규칙을 적용하되 기존 관측값을 반올림해 저장하지 않는다.
HA 엔터티 suggested_display_precision=0은 표시 설정이며 native_value 자체의 정수화와
다르다. 이번에는 정책 검토만 기록하고 센서 정밀도나 프로덕션 UI는 변경하지 않았다.
